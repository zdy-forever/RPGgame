# Task 1.2 — Work Plan

## 1. Development Strategy

### 1.1 Overall approach

- **Agile and iterative.** We use a lightweight Agile approach. We don't do a complete Scrum session but we plan in stages and short iterations to see what is left at the end of each stage.

During M2, we worked in a trunk-based way.
Every issue has a branch with the same name as the issue.

In M3, we spent about 1 to 3 days working in short rounds. 
In each round, we did the task with the highest priority.

- **Why there is no M1 milestone in GitLab.** 

Our GitLab milestone begins with M2. M1 is the initial stage of the project. 
At that stage, we discussed gameplay in the group and wrote a draft similar to game skeleton linked to ` Activity_1/Game_skeleton.md'.
Because this work was done by group discussion and sharing documents instead of code, it is difficult to express it as an issue of GitLab, which did not create a milestone. 
M2 to M6 cover all the work after the first code.

- Bugs and improvement ideas discovered during development will become the new issue in milestone, just like the planned task.
### 1.2 Stages as GitLab milestones

Each stage of the project is a milestone of GitLab, and the date range is determined. 
All issue belong to milestone, so look at milestone's page to know how much each stage has progressed.

### 2.1 Order of work

The **Prerequisites** column in Section 3 gives the exact dependencies. In short the work has to go in
this order:

```text
Collision and maps
  → Health → Combat pipeline
    → Classes and skills, enemy AI → Boss → Elemental reactions
      → Quest-gated battles and battle results
        → NPC dialogue and quests, inventory rewards (these need battle results)
          → Save / load (needs snapshots from every module, so it comes last)
```
